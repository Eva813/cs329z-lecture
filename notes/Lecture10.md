整講的主線：**軟體開發正從「演繹式」走向「歸納式」，所以在 agent 的世界裡，評測取代程式碼成為真相的來源（p.20、p.40）。**

### 1. 從演繹式到歸納式（p.2–29）

| | 演繹式（p.11） | 歸納式（p.15） |
|---|---|---|
| 公式 | 規則 + 輸入 → 輸出 | 輸入 + 輸出 → 規則 |
| 人做什麼 | 寫規則（程式碼） | 給範例（資料與標籤） |
| 開發流程（p.16） | 規格 → 實作 → 測試 → 部署，一條直線 | 目標 → 評測 → 實驗 → 優化，再回到評測反覆迭代 |

- **所有數位技術開發都在變成歸納式（p.19–20）**：模型從資料學出來、agent 靠評測開發、軟體由 agent 產生。
- **電話號碼的例子（p.24–25）**：用正規表示式抽電話號碼時，讀程式碼就知道它會做什麼；換成呼叫 LLM 後，程式碼裡只剩一句「Extract the phone number」，它會輸出什麼只能跑例子看。真相的來源從規則移到了輸出。
- **規格 → 評測（p.26–28）**：寫規格的是軟體工程師，那寫評測的是誰？後半段教的就是這個角色的工作。

### 2. Harbor：評測驅動開發的工具（p.39–40）

Terminal-Bench 大約是一個基準，由團隊自己做評測；Harbor 把他們學到的經驗做成工具，讓任何人都能做自己的評測（p.39）。Harbor 的口號是「理解並改進 agent」（p.40）。

| 以前：傳統軟體 | 現在：agent 的世界 |
|---|---|
| 程式碼是真相的來源 | **評測**是真相的來源 |
| 確定性的 | 隨機的 |
| 演繹的 | 實證的 |
| 軟體是手工打造的 | 軟體是學出來的 |

### 3. 定義（p.42）

出自 Anthropic〈Demystifying Evals for AI Agents〉，中括號裡是同義詞：

| 術語 | 中文 | 意思 |
|---|---|---|
| Task | 任務 | 單一測試，有明確的輸入與成功標準 |
| Trial | 嘗試 | 對一個任務跑一次（同一任務通常跑多次，因為結果是隨機的） |
| Benchmark [Evaluation suite] | 基準［評測套件］ | 一組任務，用來衡量特定能力 |
| Verifier [Grader] | 驗證器［評分器］ | 為 agent 表現打分的邏輯 |
| Trajectory [Trace, Transcript] | 軌跡［追蹤、逐字紀錄］ | 一次嘗試的完整紀錄 |
| Evaluation harness | 評測框架 | 端到端跑評測的基礎設施（Harbor 屬於這類） |
| Agent harness | agent 框架 | 讓模型能以 agent 身分行動的系統（例如 Claude Code、Codex） |

最容易搞混的是最後兩個：agent harness 包住**模型**，讓它能用工具；evaluation harness 包住 **agent**，讓它能被大量、可重現地測。

### 4. Harbor 的任務格式（p.43）

```text
my-task/
├── instruction.md      # 給 agent 的指令
├── task.toml           # 設定（時間限制、資源等）
├── environment/
│   └── Dockerfile      # agent 工作的環境
├── solution/
│   └── solve.sh        # 參考解答
└── tests/
    └── test.sh         # 驗證器
```

（註解是導讀補充的；投影片沒有列出 task.toml 的具體欄位。）這種格式要達到五個性質：

- **與 agent 無關**：任何 agent 都能拿來跑，不綁定某個產品。
- **容易定義**：一個資料夾、幾個檔案就是一個任務。
- **可攜**：靠 Docker，在本機或雲端都能跑。
- **表達力強**：只要能在容器裡做的事都能當任務。
- **彼此獨立**：每個任務自成一體，不依賴其他任務。

對照 p.38 的 STEP 檔任務範例：instruction.md、environment/、tests/ 正好是那三個部分，再加上 solution/（p.53）和設定檔。

### 5. 怎麼寫好一個任務（p.44–55）

**三個原則（p.44）**，副標是兩個問題：你在量什麼？你量得對嗎？

- **指令與驗證器要對齊**：指令要求的事，驗證器都要檢查；驗證器檢查的事，指令都要講到。
- **防止 reward hacking**：不讓 agent 用作弊的方式拿到分數。
- **真實、公平、有趣**：任務要像真實工作，不能藏陷阱，也要值得測。

**驗證器（p.49）**：驗證器是以結果為準、對環境最終狀態做判斷的分類器。

- **混淆矩陣**：把驗證器當分類器看，它也會誤判。偽陽性（沒做對卻通過）會高估 agent，偽陰性（做對卻沒通過）會低估 agent。（投影片寫「FP/NP/TP/TN」，NP 應是 FN 的筆誤。）
- **和指令裡的要求一對一對應**：每條要求有一個檢查，每個檢查都對應一條要求。p.38 的九個 assert 就是例子。
- **兩種做法**：程式化檢查，以及讓 agent／LLM 當評審。

**Reward hacking 的三道防線（p.51）**

- **鎖住 agent 的環境**：限制 agent 能接觸的東西。
- **驗證器環境隔離**：測試檔不放在 agent 的環境裡。agent 看不到測試，就無法照著測試硬湊答案，也不能直接改測試。
- **agent 程式碼執行隔離**：驗證時不在 agent 動過手腳的環境裡跑。

```text
Agent 環境（agent 在這裡產出成品）
   └─ 只把成品（artifact）搬過去 ─→ 驗證器環境（成品 ＋ 測試）
```

真實案例（p.52）：有模型在 Terminal Bench Science 上網搜尋 Lean 核心的已知 bug，再利用它寫出能騙過評分器的「證明」。開放上網更真實，但也有這種代價。

### 6. 評測基礎設施與長期維護（p.56–63）

這一段講：怎麼把評測跑得可靠又快、上線前怎麼替任務做品管、任務出 bug 怎麼修、版本怎麼編、結果怎麼呈現。

**版本號規則（p.61）**：借用語意化版本號 x.y.z，但每一位數代表舊結果還能不能用：

| 版本變動 | 改到什麼 | 舊結果怎麼處理 | 例子 |
|---|---|---|---|
| (x+1, y, z) | agent 環境 | **重跑**（rerun） | 新任務、修正指令寫太少或太多、修改資料與工具、調整 agent 資源 |
| (x, y+1, z) | 驗證器 | **重新評分**（regrade）：軌跡不用重跑，用新驗證器重新打分 | 修正太嚴的驗證器、堵掉 reward hack、重新調整評審、降低驗證器不穩定、調整驗證器資源、回報額外指標、更改獎勵 |
| (x, y, z+1) | 中繼資料 | **沿用**（reuse） | 更新文件、修正 oracle 不穩定、鎖定會變動的依賴版本、修正指令中的錯字 |

這套規則的價值在於省錢：只有真的改到 agent 所見的環境時，才需要花大錢把所有模型重跑一遍。

#### 自我檢查參考答案

> **Q1：用電話號碼例子說明，為什麼換成 LLM 後「真相的來源」從規則變成了輸出？和 p.16 的兩條生命週期有什麼關係？**
>
> **正規表示式版本（p.24）：規則就寫在程式碼裡。** 讀 `re.search(r"\d{3}-\d{3}-\d{4}", text)` 就能推出它對任何輸入的行為：`555-123-4567` 抓得到；`(555) 123 4567` 格式不符，`match` 是 `None`，`.group()` 會報錯。連它在哪裡壞都能事先推出來，所以讀規則就知道它對不對，這是 p.10 Hoare 說的演繹。
>
> **LLM 版本（p.25）：程式碼裡沒有規則了。** 只剩一句「Extract the phone number」，決定行為的規則藏在模型權重裡，人讀不到。遇到 `(555) 123 4567`、國際號碼、兩支號碼、沒有號碼時會怎麼做，都推不出來；同樣的輸入每次輸出還可能不同。唯一的辦法是準備大量輸入、實際跑、檢查輸出，所以真相的來源變成「一組輸入和預期輸出的評測集」，也就是 p.15 的歸納式。
>
> **和 p.16 的關係：**
>
> | | 軟體工程生命週期（演繹式） | ML 生命週期（歸納式） |
> |---|---|---|
> | 流程 | 規格 → 實作 → 測試 → 部署 | 目標 → 評測 → 實驗 → 優化，再回到評測 |
> | 測試／評測的角色 | 實作之後的驗收；正確性主要來自規則本身 | 一切的起點，也是迭代的中心 |
> | 電話號碼例子 | 寫好 regex，補幾個測試就上線 | 先建評測集，量準確率 → 改 prompt 或換模型 → 再量，反覆迭代 |
>
> 把實作換成 LLM，這個小程式就從上面那條生命週期搬到了下面那條。這也是 p.22 把上面那條改標成「舊的」軟體工程生命週期的原因。

> **Q2：Harbor 任務資料夾有哪幾個部分？驗證器為什麼要放在和 agent 隔離的環境裡跑？**
>
> | 部分 | 用途 |
> |---|---|
> | `instruction.md` | 給 agent 的指令，要完整明確、盡量精簡、盡量自然（p.45） |
> | `task.toml` | 任務設定（時間限制、資源等；投影片沒列欄位） |
> | `environment/Dockerfile` | agent 工作的環境，盡量貼近正式環境，網路依賴先打包進去（p.47） |
> | `solution/solve.sh` | 參考解答，證明任務做得出來，也用來替驗證器和環境除錯（p.53） |
> | `tests/test.sh` | 驗證器，檢查環境最終狀態，和指令裡的要求一對一對應（p.49） |
>
> **為什麼要隔離（p.51）：** 如果測試和 agent 在同一個環境裡，agent 可能讀測試照著湊答案、直接改掉或刪掉測試，或竄改測試依賴的工具和函式庫。這些都會造成**偽陽性**（沒做對卻通過），高估 agent 的能力。所以只把成品搬到乾淨的驗證器環境裡檢查：agent 看不到測試，也碰不到執行測試的環境。p.52 的案例說明這不是多慮：模型越強，越會主動找評分器的漏洞。
>
> 參考解答也要模仿 agent 的做法、不能寫死答案（p.53），因為它要證明的是「正常解法能通過驗證器」。

> **Q3：修正了一個太嚴格的驗證器，版本號升哪一位？舊結果怎麼處理？**
>
> **升中間那一位 (x, y+1, z)，舊結果重新評分（regrade）。** 判斷的關鍵是 agent 看到的東西有沒有變：
>
> - agent 看到的指令和環境都沒變，它當初的行為仍然有效，所以**不用重跑**（不是 x）。
> - 但驗證器變寬鬆後，有些以前判失敗的嘗試其實是做對的（之前是偽陰性），分數會變，所以**不能直接沿用**（不是 z）。
> - 做法：拿已存下的成品和軌跡，用新驗證器重新打分。這也是 p.62 要「每一列附完整收據」的原因：沒存成品就只能重跑。
>
> **容易判斷錯的情況：** 如果驗證器太嚴，根本原因是指令沒寫清楚，修正時連指令也改了，那就動到了 agent 看到的東西，要升 x、全部重跑。
