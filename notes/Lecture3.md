# Lecture 3 精煉筆記：RAG + Agents

> **一句話總結**：模型記不住、也不知道私有或最新的資料，所以在需要時把相關資料檢索出來交給它。這講的重點是三件事：怎麼建索引、怎麼搜、會壞在哪裡。最後讓 agent 自己決定要不要查。

**學習目標**（p.9）
- 學會 RAG 流程**怎麼搭起來**、**在哪裡會壞**。
- 知道**該把什麼建成索引**，以及**怎麼搜尋**它。

## 1. 為什麼要檢索（p.10–11）

核心想法：不要求模型記住所有事情，而是在**需要的當下（just-in-time）**把相關內容提供給它。這就是 Lecture 2「用檢索取代全塞」那條上下文工程技巧。

| 好處 | 說明 |
|---|---|
| **動態** | 要更新或新增知識，只要改文件庫，不必重新訓練模型 |
| **可解釋** | 模型可以標出根據哪些文件回答（引用來源），方便人查證 |

## 2. RAG 論文的核心（Lewis et al., 2020） *補充自論文*

用「開書考試」來想：

| 論文用語 | 白話 | 在 RAG 裡是 |
|---|---|---|
| 參數記憶 parametric memory | 腦袋裡背的東西 | 生成器 BART 的權重 |
| 非參數記憶 non-parametric memory | 可以翻的參考書 | 維基百科切成 2100 萬個 100 詞區塊，建成向量索引 |
| 檢索器 p(z\|x) | 翻書找相關段落 | DPR：問題和段落各轉成一個向量，比內積 |
| 生成器 p(y\|x,z) | 看著段落寫答案 | BART：把問題和段落串在一起輸入 |

- **不知道哪段才對，就每段都試**：取前 K 段，每段各算一次答案的機率，再依檢索器對該段的信心加權加總。
  - RAG-Sequence：整個答案用同一段。
  - RAG-Token：每個字都可以換段。
- **訓練不需要標註「哪段是對的」**：只要有問題和答案，答對的段落自然會被加權加總推高。
- **結果**：自然問題（NQ）資料集上 RAG 拿到 44.5 分，可訓練參數約 6 億；只靠模型記憶的 T5-11B（110 億參數）只有 36.6。
- **換書就能更新知識**：把索引換成不同年份的維基百科，不用重新訓練，就能回答那一年的世界領袖（約 70% 答對）；年份不對時只剩 4–12%。

## 3. 建索引：切塊與情境化（p.24–28）

### 切塊方式

| 方式 | 做法 | 注意 |
|---|---|---|
| 固定大小 | 每塊 100–500 token | 太小缺乏上下文；太大一個向量混了好幾個主題 |
| 重疊 | 相鄰區塊重疊 10–20% | 避免句子在邊界被切斷 |
| 語意切塊 | 依句子、章節等邏輯邊界切 | p.25 例子：依標題切最完整 |
| 補充上下文 | 每塊附上中繼資料或摘要 | 就是下面的情境化檢索 |
| AI 動態切塊 | 讓 LLM 找自然斷點 | 成本較高 |

### 情境化檢索（Contextual Retrieval）

問題：切出來的區塊常常失去它在原文件中的背景。

| | 內容 | 結果 |
|---|---|---|
| 查詢 | 「ACME 公司 2023 年第二季的營收成長多少？」 | |
| 原區塊 | 「該公司營收較上一季成長 3%。」 | ✗ 沒提到公司和季度，比對不上 |
| 情境化區塊 | 「出自 ACME 公司 2023 年 Q2 的 SEC 申報文件；Q1 營收為 3.14 億美元。該公司營收較上一季成長 3%。」 | ✓ |

- **做法**（p.28）：把整份文件和這個區塊一起交給 LLM，請它寫一段簡短背景，加在區塊前面再建索引。
- **混合檢索**（p.27）：嵌入向量擅長抓語意，BM25 擅長抓精確字詞，兩邊結果再合併。

### ❓ 所以應該要如何設定檢索？實作方法為何？ *整理自投影片 + 補充*

一條常見的 RAG 流程，照順序做：

| 步驟 | 做什麼 | 對應投影片 |
|---|---|---|
| 1. 切塊 | 先從 300–500 token、重疊 10–20% 開始；文件有標題就依標題切 | p.24–25 |
| 2. 補背景（選用） | 用 p.28 的 prompt 請 LLM 幫每塊寫背景 | p.26–28 |
| 3. 建兩種索引 | 每塊轉成向量，存進向量資料庫；同時建 BM25 關鍵字索引 | p.27、36、41 |
| 4. 查詢 | 兩種索引各撈前 20–50 個，用 RRF 合併 | p.49 |
| 5. 重排序（選用） | 用交叉編碼器對前幾十個重新排序，取前 3–5 個 | p.50 |
| 6. 放進 prompt | 把這幾塊連同來源一起交給 LLM，要求附上引用 | p.11 |
| 7. 評估 | 準備一批「問題 → 正確文件」，量 Recall@k，再調整前面的參數 | p.45–46 |

- **常用工具**（補充，投影片沒寫）：向量資料庫可以用 FAISS、Chroma、pgvector；框架有 LlamaIndex、LangChain。
- **參數只是起點**：上面的數字都是常見起始值，沒有標準答案，要用步驟 7 的評估來調。這和 Lecture 2「用 eval 實際測」是同一件事。

## 4. 檢索器（p.40–54）

| 檢索器 | 怎麼比對 | 擅長 | 弱點 | 延遲 |
|---|---|---|---|---|
| **BM25** | 關鍵字重疊（罕見詞權重高） | 編號、名稱、錯誤代碼 | 換句話說、同義詞 | 62 ms |
| **DPR** | 問題和段落各一個向量，比內積 | 語意相近 | 罕見字面字串；需要標註資料 | 數十 ms |
| **ColBERT** | 每個 token 一個向量，MaxSim | token 層級的證據 | 索引很大 | 458 ms |
| **交叉編碼器** | 問題和段落一起進模型 | 最準 | 只能用在短名單上 | 每 1,000 段 10,700 ms |

實務做法：先用便宜的檢索器撈廣，再用貴的模型排準。

### 混合搜尋與倒數排名融合（RRF，p.49）

- **為什麼要混合**：兩種檢索器失敗的方式不同。BM25 抓不到換句話說；稠密檢索抓不到罕見的字面字串，例如錯誤代碼、產品編號。
- **混合搜尋**：兩種都跑，再把兩份排名清單合併。
- **RRF**：合併時用**名次**而不是原始分數。

### ❓ RRF 公式需要理解嗎？

**觀念要懂，公式不用背。** 只要記住三句話：

1. **只看名次，不看分數**：BM25 的分數可能是 12.3，向量相似度是 0.82，兩者尺度不同，不能直接相加；名次則永遠可以比。
2. **每個檢索器給的分數是 1 / (60 + 名次)**：第 1 名得 1/61，第 2 名得 1/62，越後面越少。
3. **把各檢索器的分數加總**：兩邊都排前面的文件，分數最高。

| 文件 | BM25 名次 | 向量名次 | RRF 分數 |
|---|---|---|---|
| A | 1 | 沒撈到 | 1/61 ≈ 0.0164 |
| B | 2 | 2 | 1/62 + 1/62 ≈ 0.0323 ✓ 勝出 |

- **k = 60 的作用**：讓名次之間的差距變小（第 1 名 0.0164，第 10 名 0.0143），避免某個檢索器的第 1 名獨大。60 是原論文的經驗值，照用即可。
- **實作上**：多數向量資料庫和框架都有內建 RRF，通常不用自己寫。

## 5. Agentic RAG：檢索變成 agent 的一個動作（p.56–61）

前面的方法都能把一個問題答好，但沒有一個會決定要不要查、查什麼、查夠了沒。所以**檢索應該是 agent 的一個動作**，和呼叫其他工具一樣。

agent 要做三個決定：① 要檢索，還是直接回答 → ② 下什麼查詢 → ③ 結果夠好了嗎

這就是 Lecture 1 的 ReAct 迴圈套用在檢索上。

| 方法 | 做法 |
|---|---|
| Self-RAG | 模型學會自己判斷要不要查，並評論查到的內容 |
| CRAG | 由評估器替檢索結果打信心分數，決定下一步 |
| Search-R1 | 用強化學習訓練「什麼時候搜、搜什麼」 |

### ❓ 所以這是現在主流方式？ *補充，投影片沒寫*

**兩種並存，依任務選。**

| | 固定流程 RAG（每次查一次） | Agentic RAG（agent 決定怎麼查） |
|---|---|---|
| 常見場景 | 客服、公司文件問答、FAQ | 程式碼 agent、深度研究、需要多步推理的問題 |
| 優點 | 便宜、快、可預測、好除錯 | 能處理複雜問題，查不到會換個方式再查 |
| 缺點 | 第一次沒查到就答不好 | 慢、貴，可能一直查不停（見下一段的迴圈端問題） |

- **趨勢**：需要多步推理的產品越來越常採用 agentic 做法。例如 Claude Code 這類程式碼 agent，主要是讓模型自己用 grep、讀檔等工具去找，而不是事先建好向量索引。
- **選擇原則**：和 Lecture 2〈Building Effective Agents〉一樣。先用最簡單的固定流程，評估後發現不夠，再升級成 agentic。

## 6. RAG 的問題（p.63）

### ❓ 這是使用 RAG 要注意的事項嗎？

**是。** 這張表有兩種用途：設計時當**檢查清單**，答錯時當**除錯清單**。除錯時依序檢查證據有沒有撈到（檢索端）→ 模型有沒有用對（閱讀端）→ 迴圈有沒有失控。

右欄的對策是我補充的，投影片只列出問題。

| 位置 | 問題 | 意思 | 常見對策 |
|---|---|---|---|
| **檢索端** | 召回上限 | 證據沒被撈到，模型再強也答不出來 | 混合搜尋、改善切塊、量 Recall@k |
| | 索引過期 | 文件更新了，向量沒跟著更新 | 文件變動時自動重建索引 |
| | 權限外洩 | 用到使用者無權看的內容 | 檢索時就依使用者權限過濾 |
| **閱讀端** | 迷失在中間 | 上下文中段的資訊容易被忽略 | 少給幾段、重排序後把最相關的放前面 |
| | 分心 | 相似但無關的內容干擾回答 | 重排序、設定相關度門檻 |
| | 證據衝突 | 來源互相矛盾，或和模型知識衝突 | 要求附引用、優先採用較新的來源 |
| **迴圈端** | 錯誤累積 | 早期錯誤影響後面所有決定 | 每步驗證中間結果 |
| | 沒有停止條件 | 不知道何時算完成 | 設定最多步數或預算 |
| | 提示注入 | 檢索到的文字反過來操控 agent | 把檢索內容當資料而不是指令；限制 agent 權限 |
