## 1. 為什麼 agent 工程師要懂底層（投影片 p.91）

- Agent 要處理**非常長的上下文**。
- **推論效率**是設計 agent 系統時要考慮的因素。
- 了解底層架構，才能為應用**選對模型**。
- 依照模型的強項與弱點來設計 **harness / scaffolding**。

> 讀這講時一直問自己：「這個設計會讓 agent 有什麼限制？」

## 2. 上下文工程（Context Engineering）

**定義**：在 LLM 推論期間，挑選並維護「最佳 token 集合」的一組策略。範圍不只 prompt，還包括系統指令、工具、MCP、外部資料、訊息歷史等**整個上下文狀態**。

**和提示工程的差別**：提示工程關心怎麼寫好一段 prompt；上下文工程關心多輪、長時間運作的 agent 在每一步該讓模型看到什麼。

### 為什麼不能全部塞進去

- **上下文腐化（context rot）**：上下文越長，模型的推理與整合能力越差（投影片 p.163–164）。*補充自投影片*
- **工具太多也會失敗**：工具涵蓋太多功能，或「該用哪個工具」的決策點很模糊。投影片的例子是 Pi，這個程式碼 agent 只用 read、write、edit、bash 四個工具。

### 長時間任務的三種技巧

| 技巧 | 做法 | 適合 |
|---|---|---|
| **壓縮**（compaction） | 上下文快滿時摘要成精簡版本，用新上下文接續 | 需要大量來回互動、要維持對話流的任務 |
| **結構化筆記**（agentic memory） | Agent 定期把筆記寫到上下文之外的儲存，需要時再拉回來（如 Claude Code 的 todo list、`NOTES.md`） | 有清楚里程碑的迭代式開發 |
| **子 agent 架構** | 主 agent 規劃與協調；子 agent 帶著乾淨的上下文做深入工作，可能用掉數萬 token，但只回傳 1,000–2,000 token 的摘要 | 可以平行探索的複雜研究與分析 |

- 子 agent 的價值在於**關注點分離**：搜尋細節被隔離在子 agent 裡，主 agent 只負責綜合。
- 壓縮的兩難：留太多，很快又要再壓縮；丟太多，可能失去關鍵資訊。

### 和模型機制的連結：KV Cache（投影片 p.168–169） *補充自投影片*

- 新內容一律**接在最後面**。在前面插入或修改內容，後面所有 token 的 KV Cache 都要重算，變慢又變貴。
- 每次修改上下文策略，都要**用 eval 實際測**效果（p.170）。上下文的建構方式沒有唯一正解，這正是 HW1 要實驗的內容。

## 3. Building Effective Agents

**核心判斷**：最成功的實作通常不用複雜框架，而是用**簡單、可組合的模式**。先用簡單的 prompt 加上完整的評測，只有簡單方案不夠時才升級成多步 agent。

### Workflow vs. Agent

| | Workflow（工作流） | Agent |
|---|---|---|
| 誰決定流程 | 預先寫好的程式路徑 | LLM 自己動態決定流程與工具 |
| 特性 | 可預測、一致 | 有彈性，但成本與出錯風險較高 |
| 適合 | 步驟固定、可以拆清楚的任務 | 開放式、步驟無法預先知道的任務 |

**最小構建塊：增強型 LLM**，也就是 LLM 加上**檢索 + 工具 + 記憶**，可以透過 MCP 接入工具生態。

### 五種工作流模式

| 模式 | 做法 | 什麼時候用 | 例子 |
|---|---|---|---|
| **提示鏈** Prompt Chaining | 固定的子任務依序串接，中間可以加檢查 | 任務能乾淨拆成固定步驟；**用延遲換準確率** | 寫行銷文案 → 翻譯；寫大綱 → 檢查 → 寫全文 |
| **路由** Routing | 先分類，再導向專門的流程 | 類別明顯，而且分開處理效果更好 | 客服分流（諮詢／退款／技術）；簡單題給 Haiku、難題給 Sonnet |
| **平行化** Parallelization | **分區**：拆成獨立部分同時跑；**投票**：同一任務跑多次再彙整 | 可以平行加速，或需要多角度提高信心 | 分區：回答與護欄分開跑；投票：多個 prompt 一起審查程式碼漏洞 |
| **編排者-執行者** Orchestrator-workers | 中央 LLM 動態拆解任務、分派給執行者，再整合結果 | **事先無法預測需要哪些子任務** | 要改多個檔案的程式任務；多來源的搜尋研究 |
| **評估者-優化者** Evaluator-optimizer | 一個 LLM 生成，另一個 LLM 評估並給回饋，循環改進 | 有清楚的評估標準，而且迭代能帶來可衡量的進步 | 文學翻譯；需要多輪搜尋的複雜查詢 |

> 路由和編排者-執行者容易搞混：路由是**分類後交給既有的固定路徑**，編排者-執行者是**當場決定要拆成哪些子任務**。

### 實作 agent 的三條原則

1. **簡單**（simplicity）：保持 agent 的設計簡單。
2. **透明**（transparency）：把 agent 的規劃步驟明確展示出來。
3. **打磨 ACI**（agent-computer interface）：把工具文件和測試做好，像設計給人用的 UI 一樣用心。

---

## 4. 可驗證獎勵的強化學習（RLVR，投影片 p.116）

- 獎勵改成**能自動驗證**的，不靠人評分。例如單元測試、Lean 證明、答案完全比對、檢查系統狀態。
- 特別適合數學和程式碼，但**驗證器要設計好**，否則模型會鑽漏洞。
- **對 agent 的意義**：只要任務結束時能檢查「系統狀態對不對」，就能用 RL 訓練 agent。SWE-smith 就是大量產生這類任務來訓練程式碼 agent。

## 为 AI Agent 做高效的上下文工程
上下文工程指的是一组策略,用于在 LLM 推理期间策展并维护最优的 token(信息)集合——包括提示之外所有可能进入上下文的信息

提示工程的核心是如何写出有效的提示,尤其是系统提示。然而,随着我们转向构建更强大的 Agent——在多轮推理和更长的时间跨度上运行——我们需要管理整个上下文状态(系统指令、工具、模型上下文协议(Model Context Protocol, MCP)、外部数据、消息历史等)的策略。

造成失敗原因之一::覆盖了太多功能,或在「该用哪个工具」上产生模糊的决策点

结构化笔记,或者说智能体记忆(agentic memory),是这样一种技术:Agent 定期把笔记写入持久化于上下文窗口之外的存储,这些笔记之后会被拉回上下文窗口。

这一策略以最小的开销提供了持久记忆。就像 Claude Code 创建待办清单,或你的自定义 Agent 维护一个 NOTES.md 文件,这个简单的模式让 Agent 能在复杂任务间跟踪进度,保住那些 otherwise 会在几十次工具调用中丢失的关键上下文与依赖。


### 子智能体架构(Sub-agent Architectures)
子智能体架构提供了绕过上下文限制的另一种方式。与其让一个 Agent 试图在整个项目上维持状态,不如让专门的子智能体带着干净的上下文窗口处理聚焦的任务。主智能体用高层计划做协调,而子智能体执行深度技术工作或使用工具查找相关信息。每个子智能体也许会大量探索、消耗数万甚至更多 token,但只返回其工作的浓缩蒸馏摘要(通常 1,000–2,000 个 token)。

这种方式实现了清晰的关注点分离——详细的搜索上下文被隔离在子智能体内部,而主智能体专注于综合与分析结果。
压缩为需要大量来回交互的任务维持对话流;
笔记法适合有清晰里程碑的迭代式开发;
多智能体架构处理并行探索能带来红利的复杂研究与分析。

## Building Effective Agents
最重要的判断:最成功的实现往往不用复杂框架,而是用简单、可组合的模式。

关键概念区分——工作流(workflows,由预定义代码路径编排 LLM 与工具)与 Agent(LLM 动态主导自身流程与工具使用),然后从最小构建块「增强型 LLM」出发,逐级介绍五种工作流模式(提示链、路由、并行化、编排者-执行者、评估者-优化者)与自主 Agent,并说明各自的适用场景与例子。


工作流:提示链(Prompt Chaining)
提示链适用于任务可以轻松、干净地分解为固定子任务的场景。其主要目标是以延迟换更高准确率——让每次 LLM 调用面对更简单的任务。

提示链有用的例子:

生成营销文案,再把它翻译成另一种语言。
先写文档提纲,检查提纲是否满足一定标准,再基于提纲写出文档。

### 工作流:路由(Routing)
并将其导向专门的后续任务。这种工作流实现了关注点分离,可以构建更专门的提示。没有它,针对一类输入的优化可能损害其他输入上的表现。
路由适用于存在明显类别、分别处理效果更好的复杂任务,且分类可以由 LLM 或更传统的分类模型/算法准确完成。

路由有用的例子:

把不同类型的客服请求(一般咨询、退款申请、技术支持)导向不同的下游流程、提示与工具。
把简单/常见问题路由给 Claude Haiku 4.5 这类更小、更具成本效益的模型,把困难/罕见问题路由给 Claude Sonnet 4.5 这类更强模型,以优化整体表现。

### 工作流:并行化(Parallelization)

分区:实现护栏(guardrails),一个模型实例处理用户查询的同时另一个筛查不当内容或请求——这往往比让同一次 LLM 调用同时负责护栏和核心回答效果更好;自动化评估(eval),每次 LLM 调用评估模型在给定提示上表现的不同方面。
投票:审查一段代码的漏洞,多个不同提示各自审查并在发现问题时标记;评估给定内容是否不当,多个提示评估不同方面或要求不同投票阈值,以平衡假阳性与假阴性


### 工作流:编排者-执行者(Orchestrator-workers)
这种工作流适合无法预测所需子任务的复杂工作(例如编程中,需要改动的文件数量和每个文件的改动性质可能取决于具体任务)。
有用的例子:

每次需要对多个文件做复杂修改的编程产品。
需要从多个来源收集并分析可能相关信息、用于综合研判的搜索任务。

### 工作流:评估者-优化者(Evaluator-optimizer)
在评估者-优化者工作流中,一次 LLM 调用生成回答,另一次调用在循环中提供评估与反馈。

[图:评估者-优化者工作流——生成者 LLM 与评估者 LLM 循环迭代]

何时使用此工作流:

当我们有清晰的评估标准、且迭代精炼能带来可衡量的价值时,这种工作流尤其有效。两个契合信号是:其一,当人类清晰表达反馈意见时,LLM 的回答可以被证明得到改进;其二,LLM 自己能提供这样的反馈。这类似人类作者打磨文档时的迭代写作过程。

评估者-优化者有用的例子:

文学翻译:译者 LLM 起初可能抓不住细微之处,而评估 LLM 能给出有用的批评。
需要多轮搜索与分析才能收集全面信息的复杂搜索任务,由评估者决定是否需要进一步搜索。



---
在 LLM 领域取得成功,不在于构建最精巧的系统,而在于构建适合你需求的系统。从简单提示开始,用全面的评估来优化,只有当更简单的方案不够用时才引入多步智能体系统。

实现 Agent 时,我们尽量遵循三条核心原则:

在 Agent 设计中保持简单(simplicity);
通过显式展示 Agent 的规划步骤来优先保证透明度(transparency);
通过完善的工具文档和测试,精心打磨你的智能体-计算机接口(agent-computer interface,ACI)。


关键区分:工作流(workflows)= 预定义代码路径编排 LLM 与工具,可预测、一致;Agent = LLM 动态主导自身流程与工具使用,适合需要灵活性与模型决策的开放任务。
最小构建块是增强型 LLM:检索 + 工具 + 记忆;可通过 MCP 等协议接入工具生态。
五种工作流模式:提示链(以延迟换准确率)、路由(分类后分流,如 Haiku 处理简单问题、Sonnet 处理难题)、并行化(分区 + 投票)、编排者-执行者(动态拆分委派子任务,适合多文件编程)、评估者-优化者(生成-评估循环,适合文学翻译等迭代精炼)。
