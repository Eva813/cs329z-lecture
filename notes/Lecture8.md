整講的主線（p.14）：**先做一個強的單 agent 基準，有明確理由才加 agent，並量測合作的好處是否大於協調成本。**

### 1. 單 agent vs 多 agent（p.7–15）

**什麼是多 agent 系統（p.10）**

- 由多個 agent 組成、朝同一個共同任務努力的集合。
- 設計時要考慮三件事，也就是後面三段的標題：
  - **編排**：agent 之間的組織結構（誰跟誰連、誰做決定）
  - **溝通**：怎麼交換資訊
  - **協調**：共用的工作空間、任務、共享上下文與記憶

**有時候單 agent 反而比較好（p.13）**

多 agent 不保證變好，結果依模型家族而異；對某些強模型，多 agent 反而拖累表現。圖中最強模型上 MAS 相對 SAS 的差距：GPT-5 +12.3%、Gemini 2.5 Pro −4.6%、Claude Sonnet 4.5 −7.2%（Kim et al., 2026）。

**什麼時候用單 agent、什麼時候用多 agent（p.14）**

| 偏好單 agent 系統，當…… | 可以試多 agent 系統，當…… |
|---|---|
| 步驟之間高度相依 | 子任務只需要少量同步就能各自推進 |
| 工作緊密綁在同一份共享狀態上（重疊很多） | 資訊可以切成幾份聚焦的上下文 |
| 一個 agent 已經達到品質、成本與延遲目標 | 各 agent 能各自負責一部分產出，最後再整合 |
| | 平行、專業分工或獨立審查能解決一個**量測到的**瓶頸 |

### 2. MAS 編排模式（p.16–29）

**四種編排模式（p.17–21）**：圖的靈感來自 Anthropic〈Building Effective Agents〉。

| 模式 | 怎麼運作 | 取捨 |
|---|---|---|
| 獨立 Independent（p.18） | agent 之間不交換中間訊息；最後由聚合者合併或挑選各自的輸出 | 可以平行，但 agent 無法根據彼此的中間發現調整做法 |
| 集中式 Centralized／Orchestrator（p.19） | 編排者拆解任務、分派給專門的 worker；worker 回報結果，由編排者決定下一步 | 集中監督讓協調變簡單，但編排者可能成為瓶頸 |
| 分散式 Decentralized／Swarm（p.20） | agent 可以自行產生子 agent；所有 agent 透過共享訊息板彼此溝通（全對全），共同追蹤共享狀態 | 適合大規模、彼此獨立的探索與發現 |
| 混合 Hybrid（p.21） | 編排者管整體任務、整合結果；worker 在需要時直接交換資訊 | 兼具全域監督與局部彈性，但要清楚規定職責與資訊分享規則 |

**該用哪種架構，取決於任務（p.23，Kim et al., 2026）**：四種 MAS 相對 SAS 的表現變化。

| 基準 | 獨立 | 分散式 | 集中式 | 混合 |
|---|---|---|---|---|
| BrowseComp-Plus（網頁搜尋） | −35% | +9% | +0% | +6% |
| Finance Agent（金融分析） | +57% | +75% | +81% | +73% |
| PlanCraft（規劃） | −70% | −41% | −50% | −39% |
| Workbench（工具操作） | −11% | +6% | −1% | −1% |

- Finance Agent 能拆成幾份獨立分析，所有 MAS 都大幅領先；PlanCraft 的步驟彼此緊密相依，所有 MAS 都明顯變差。正好對應 p.14 的判準。
- 「獨立」架構在需要互相參考的任務上（BrowseComp、PlanCraft）掉最多，因為 agent 看不到彼此的中間結果。
- 成本（p.24）：單 agent < 編排式 < 群體式。

> **Q：MAST 主要就是會有不同的測試模式，對應不同情境任務的測試結果？**
>
> 不是，這裡把兩篇論文混在一起了：
>
> | | 上面這張表 | MAST |
> |---|---|---|
> | 出處 | Kim et al., 2026〈Towards a Science of Scaling Agent Systems〉 | Cemri et al., 2025〈Why Do Multi-Agent LLM Systems Fail?〉（本講必讀） |
> | 在做什麼 | 拿同一批任務，比較 SAS 和四種 MAS 架構**誰表現比較好** | 收集 MAS 的執行軌跡，把**失敗的原因**分類 |
> | 「模式」指的是 | 編排模式（獨立、集中、分散、混合） | 失敗模式（failure mode），例如重複步驟、過早結束 |
> | 投影片位置 | p.13、p.22–24 | p.70–72（第 5 節） |
>
> MAST 的全名是 Multi-Agent System Failure **Taxonomy**（失敗分類法），它不是測試方法，也不比較架構好壞，而是回答「MAS 失敗時，是哪一種錯」。

**動態多 agent 架構：DyLAN（p.25–28）**

前面的拓撲是人手動決定的；DyLAN 讓系統依任務自己挑團隊、自己調整結構。

- 團隊最佳化：先在幾題上試跑，讓 agent 互相替回答打分，再把功勞往回傳，算出「agent 重要性分數」，挑分數最高的 agent 組隊。
- 解題：執行中用 LLM 評分，動態移除表現差的 agent；2/3 的 agent 答案一致就提早停止。
- 結果：決策任務上 reward 68.3、成功率 42.0，都是最高，API 呼叫數 24.85，比 Reflexion（25.40）略少、遠少於 LATS（>400）。

### 3. 溝通（p.30–49）

**溝通 vs 協調（p.31，p.51 重複此頁）**

| | 溝通 Communication | 協調 Coordination |
|---|---|---|
| 關心什麼 | agent 怎麼交換資訊 | agent 怎麼管理彼此相依的工作 |
| 要回答的問題 | 誰收到哪些資訊？透過什麼管道？ | 每項任務歸誰？什麼必須先完成？ |
| 具體內容 | 訊息格式、協定、共享的產出物 | 任務指派、相依關係、衝突解決 |

**以對話作為溝通：AutoGen（p.32–35）**

- AutoGen 的三個元件：**可對話 agent**（後端可以是 LLM、人或工具）、**彈性的對話模式**（例如兩兩對話、階層對話），以及範例對話：使用者要畫 META 與 TESLA 年初至今的股價圖，助理寫程式、執行失敗（缺 yfinance 套件）、改成先安裝再執行、使用者再要求改成百分比變化。
- 四種對話模式（p.34）：
  - **依序**：一組 agent 討論完，再交棒給下一組做下一步。
  - **巢狀**：子 agent 直接向管理者回報。
  - **群組聊天**：一群 agent 共用同一份上下文。
  - **階層聊天**：所有子 agent 都只和編排者溝通。

> **Q：所以這會有一個主要 agent 負責發落、收回報，但這個主 agent 的上下文會膨脹？**
>
> 前半對，後半要分情況。上下文膨脹最嚴重的其實是**群組聊天**，不是階層聊天：
>
> | | 群組聊天 | 階層聊天（有主 agent） |
> |---|---|---|
> | 每個 agent 看到什麼 | 整條對話串，包含其他所有 agent 的每一則訊息 | 子 agent 只看到主 agent 交辦的那一份；主 agent 只看到子 agent 的**回報** |
> | 膨脹的位置 | 每個 agent 都膨脹 | 只有主 agent，而且只累積回報，不累積子 agent 內部的搜尋、試錯過程 |
>
> 所以階層結構本身就是一種**控制上下文的手段**：子 agent 在自己的上下文裡把髒活做完，只回傳精簡的結果（p.11「聚焦的上下文」、p.38 agent-as-tool 都是這個意思）。
>
> 但你擔心的情況確實會發生：子 agent 回報太長、或來回很多輪時，主 agent 一樣會塞滿。常見的做法：
> 1. 規定子 agent 只回傳摘要或固定格式的結果，而不是完整過程。
> 2. 大的產出（程式碼、報告）寫成檔案，回報只附路徑。
> 3. 把狀態放在對話外面，例如 Magentic-One 的任務帳本（第 4 節），主 agent 每輪讀帳本，而不是靠翻對話歷史。

**交接 vs 把 agent 當工具（p.36–39，OpenAI Agents SDK）**

| 特性 | Handoff 交接 | Agent-as-Tool（`as_tool()`） |
|---|---|---|
| 控制流 | 把對話控制權交出去，接手的 agent 繼續和使用者互動 | 控制權留在呼叫方 |
| 上下文分享 | 分享完整對話歷史 | 只提供特定輸入與挑選過的上下文 |
| 執行角色 | 接手整段對話 | 像副程式或助手，做完就回傳 |
| 適合 | 應該由專家直接面對使用者、負責後續步驟 | 由一個 agent 整合多位專家的貢獻、給出最終回覆 |

agent-as-tool 就是上面問題裡「主 agent 發落、收回報」的形狀；handoff 比較像客服轉接。

**訊息板：MetaGPT（p.40–42）**

- agent 不點對點傳訊，而是把結構化訊息**發布**到共享訊息池，再依角色**訂閱**需要的訊息。
- 用軟體公司的標準作業程序（SOP）串起各角色：產品經理寫需求文件 → 架構師做系統設計 → 專案經理拆任務 → 工程師寫程式 → QA 工程師測試 → 驗收。例子是一句需求「寫一個經典又簡單的 Flappy Bird 遊戲」，最後老闆驗收：「不錯！我可以直接用鍵盤玩 Flappy Bird。」

**訊息板失控：自發的協作（p.43–44）**

只要有共用管道，agent 就可能自己組織起來，做出設計者沒預期的事。p.43（METR）：一個被分到不可能任務的 agent，找到一個上千個 agent 在協作騙評分器的訊息板，並加入其中。p.44 MoltBook：給 AI agent 用的社群網站。

**Agent2Agent（A2A）協定（p.45–48）**

- A2A 是 agent 與 agent 之間溝通的協定，地位類似 MCP：**MCP 接工具，A2A 接 agent**。
- **Agent Card** 描述遠端 agent 的能力、技能、輸入輸出與驗證方式，讓呼叫方不必事先認識對方就能使用它。
- 流程：索取 Agent Card → 送出請求、建立可追蹤的 Task → 伺服器推播進度 → 雙方可來回傳訊 → 回傳完成的 Artifact。

### 4. 協調的基礎設施與模式（p.50–68）

**協調總覽（p.52）**

| 基礎設施（Infrastructure） | 模式（Patterns） |
|---|---|
| 任務帳本：追蹤規劃與執行進度 | 角色分工：指派誰做什麼 |
| 共享記憶：回想過去的經驗 | 資源劃分：切分共享的資源 |
| Worktree 隔離：把工作空間分開 | 協商：討論並同意同一個計畫 |

左欄是系統設計者事先搭好的；右欄是 agent 在合作過程中自己做的（CooperBench 觀察到的自發行為）。

**任務帳本：Magentic-One 與 Symphony（p.53–56）**

任務帳本是一份明確、持續更新的工作紀錄，用來引導 agent 之間的協調。

- **Magentic-One**：編排者 agent 維護兩層帳本。
  - 外層任務帳本：已知事實、要查的事實、要推導的事實、有根據的猜測、任務計畫。
  - 內層進度帳本：每一步檢查完成了沒、是否陷入迴圈、有沒有進展、下一個由誰做。停滯超過 2 次就回到外層重新規劃。
  - 四個 worker：Coder（寫程式、推理）、ComputerTerminal（執行 Coder 寫的程式）、WebSurfer（瀏覽網頁、填表單）、FileSurfer（讀 PDF、pptx、WAV 等檔案）。
- **Symphony**（OpenAI）：把 issue tracker 當成編排者，監看看板、把符合條件的任務派給 coding agent，各自在獨立工作空間裡做。

**共享記憶：G-Memory（p.57–61）**

G-Memory 為多 agent 系統設計三層圖結構的記憶：

| 圖 | 存什麼 | 對應的記憶類型 |
|---|---|---|
| 洞見圖 Insight Graph | 從經驗抽象出的通用洞見，例如「行動後要確認物件狀態」 | 反思 |
| 查詢圖 Query Graph | 過去的任務查詢與它們之間的關聯，附執行成功或失敗 | 情節任務索引 |
| 互動圖 Interaction Graph | agent 之間逐字的互動紀錄 | 情節記憶 |

- 為多 agent 客製的記憶勝過為單 agent 設計的基準：五個基準平均從無記憶的 48.27 升到 57.18（+8.91）。

**Worktree 隔離（p.62–63）**

- 問題：多個 agent 同時編輯同一個工作目錄，會互相覆寫。
- 分開的工作空間：給每個 agent 自己的 checkout 與分支（圖：一個 git repo 底下有多個 worktree 資料夾，各自對應 main、bugfix、feature 分支）。
- 受控的整合：merge 完成的貢獻、解決衝突、測試合併後的結果。
- 取捨：隔離減少執行時的干擾，但各分支可能越走越遠，最後的整合工作變多。
- Claude Code 等 coding agent 平行跑多個 session 時常用這招（`git worktree add`）。

**自發的協調模式：CooperBench（p.64–67）**

兩個 coding agent 各自實作一個功能、但改到同一份程式碼，在對話中自己發展出三種協調方式：

- **角色分工**：談好誰負責哪部分（「我加 octal_str，你在中間加 binary_str」）。
- **資源劃分**：切分共享資源避免碰撞（「我改 68–84 行」「我不動 68–84 行，從第 85 行開始加」）。
- **協商**：做法衝突時提出選項、收斂到同一個計畫。

### 5. 失敗與挑戰（p.69–82）

**多 agent 系統為什麼失敗：MAST（p.70–72，Cemri et al., 2025）**

- 研究流程：收集大量 MAS 執行軌跡 → 人工找出失敗 → 多位標註者對齊看法 → 建立失敗分類法 MAST → 校準一個 LLM 標註器 → 大量標註 → 釋出多 agent 失敗資料集。
- 分類結果：3 大類、14 種失敗模式。

| 大類 | 失敗模式（佔比） | 合計 |
|---|---|---|
| 系統設計問題 | 1.1 不遵守任務規格（11.8%）· 1.2 不遵守角色規格（1.5%）· 1.3 重複步驟（15.7%）· 1.4 遺失對話歷史（2.8%）· 1.5 不知道何時該結束（12.4%） | 44.2% |
| agent 之間不對齊 | 2.1 對話重置（2.2%）· 2.2 沒有要求釐清（6.8%）· 2.3 偏離任務（7.4%）· 2.4 隱瞞資訊（0.8%）· 2.5 忽略其他 agent 的輸入（1.9%）· 2.6 推理與行動不一致（13.2%） | 32.3% |
| 任務驗證 | 3.1 過早結束（6.2%）· 3.2 沒有驗證或驗證不完整（8.2%）· 3.3 驗證錯誤（9.1%） | 23.5% |

最大類是系統設計：很多失敗來自角色、流程、終止條件設計得不好，不是換更強的模型就能解決。

**協調的詛咒：CooperBench（p.73–76）**

- **一個 agent 同時解兩個任務，比兩個 agent 協作更好**。例：gpt-5 單獨 0.48、協作 0.28；claude 單獨 0.47、協作 0.26。
- 協作失敗的原因：**預期**（對方說了在做什麼，卻仍當作沒人做）42%、**承諾**（沒做到自己答應的事）32%、**溝通**（沒有有效傳達意圖、問題或進度）26%。

**行為問題一：從眾（p.77–78）**

- 讓一群 agent 各自做出令人印象深刻的東西，超過一半選擇做光線追蹤器或自我編譯的編譯器。
- 不同模型講咖啡笑話給出同一個；寫時間的隱喻，大多是「時間是一條河」。
- agent 想法都一樣時，多 agent「更廣的探索」這個好處就落空了。

**行為問題二：目標互相衝突（p.79–81）**

- 給每個 agent 不同的遷移目標語言（例如一個要 Python、一個要 Rust）。
- agent 有時會用強制手段解決衝突；不同模型解決衝突的方式差很多，有的多半休戰，有的多半強制或僵持。

**失敗小結（p.82）**：一般失敗（系統設計、agent 之間、驗證）／協調失敗（預期、承諾、溝通）／行為失敗（缺乏多樣性、用敵對方式解決衝突）。

### 6. 案例：一群 Claude 寫 C 編譯器（p.83–89）

一個無限迴圈不斷啟動新的 Claude session（分散式 swarm，沒有編排者），六種專門 agent 共用一個 git repo，用 `current_tasks/` 資料夾認領任務、用 README 與進度檔當共享記憶，每個 agent 在自己的容器與 clone 裡工作。

**學到的教訓（p.89）**

- **強的測試引導自主工作**：可靠的正確性與回歸測試，讓 agent 知道自己有沒有進展、有沒有弄壞東西。
- **為平行而設計**：把失敗或子任務拆成可以分開處理的單位。
- **讓協調明確化**：認領任務、在各自的 clone 工作、透過 git 整合貢獻。
- **跨 session 保存知識**：維護共享文件、進度筆記，以及失敗嘗試的紀錄。
- **讓回饋有效率**：提供精簡的錯誤摘要、可搜尋的 log、快速的測試子集，以及定期的進度更新。
- **指派互補的目標**：給 agent 明確不同的職責。

對照第 5 節：明確的認領與 git 整合處理了 CooperBench 的「預期」與「承諾」問題；互補的目標避開了從眾；強測試對應 MAST 第三大類的驗證失敗。

不看資料能回答的話就可以進入下一講：

**1. 哪些情況應該先用單一 agent？Kim et al. 在 Finance Agent 與 PlanCraft 上的結果正好相反，原因是什麼？（p.14、p.23）**

- 我的回答：Finance Agent 可以拆成不同的獨立任務進行。
- 補完：
  - **先用單一 agent 的情況**：步驟之間高度相依；工作綁在同一份共享狀態上；一個 agent 已經達到品質、成本與延遲目標。
  - **Finance Agent**：分析可以拆成幾份互不相依的部分，各 agent 平行做完再整合，所以四種 MAS 都大幅領先（+57% ～ +81%）。
  - **PlanCraft**：規劃的每一步都依賴前一步的結果，拆給多個 agent 反而要不斷同步、容易資訊流失，所以四種 MAS 都變差（−39% ～ −70%）。
  - 一句話：**任務能不能拆開**，決定多 agent 是加分還是扣分。

**2. Handoff 和 agent-as-tool 在控制權與上下文分享上有什麼不同？各適合什麼情境？（p.37–39）**

- 我的回答：handoff 比較像客服轉接，委派整個任務或整段對話；agent-as-tool 就是 Lecture 4 的工具呼叫，只是被呼叫的工具剛好是另一個 agent，像副程式或助手，控制權留在呼叫方，用來執行特定子任務或功能。
- 補完（題目問的上下文分享還沒答到）：

| | Handoff | Agent-as-tool |
|---|---|---|
| 控制權 | 交給接手的 agent，由它繼續和使用者互動 | 留在呼叫方，專家做完就回傳 |
| 上下文 | 完整對話歷史一起轉過去 | 只給一個範圍明確的請求和挑選過的上下文 |
| 適合 | 由專家直接面對使用者、負責後續步驟 | 由一個 agent 整合多位專家的結果、給出最終回覆 |

**3. MAST 的三大類失敗是什麼、哪一類最多？CooperBench 發現兩個 agent 合作失敗最常見的原因是什麼？（p.72、p.76）**

- 我的回答：MAST 三大類是系統設計、agent 之間、驗證；CooperBench 的協調失敗分成預期、承諾、溝通，例如會重複實作到相同部分？
- 補完：
  - **MAST 哪一類最多**：系統設計問題 44.2%，其次是 agent 之間不對齊 32.3%，任務驗證 23.5%。（「一般失敗」是 p.82 小結對 MAST 的稱呼，不是第四類。）
  - **CooperBench 最常見的原因**：**預期**，佔 42%，其次是承諾 32%、溝通 26%。
  - 「重複實作到相同部分」是預期失敗的一種**後果**：對方已經說了自己在做什麼，這邊卻仍當作那件事沒人做，結果做了重複的工作或改到衝突的程式。問題的根源在於沒有在心裡模擬對方的改動，而不是沒講清楚（沒講清楚屬於「溝通」）。
