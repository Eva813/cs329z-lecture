什麼是多 agent 系統 What is a Multi-Agent System? 重點

  • 定義：由多個 agent 組成、朝同一個共同任務努力的集合。
  • 設計 MAS 時必須考慮三件事：編排（agent 之間的組織結構）、溝通（怎麼交換資訊）、協調（共用的工作空間、任務、共享上下文與記憶）。

這三個詞就是 Part 2、3、4 的標題，後面每個系統都可以用這三題去拆。

多 agent 的好處與壞處 Benefits / Drawbacks of Multi Agent Systems 重點

好處（p.11）壞處（p.12）
平行執行：可以拆開的子任務同時做協調開銷：委派、傳訊、整合都要花時間和 token
專業分工：為不同職責量身調整指令、模型與工具資訊流失：交接時可能漏掉下一個 agent 需要的上下文
聚焦的上下文：每個 agent 只拿到和自己任務相關的資訊行動衝突：重複做同一件事、違反承諾、覆寫彼此的修改
更廣的探索：同時調查不同來源、假設或解法錯誤傳播：一個 agent 的錯會誤導其他 agent
工程複雜度：角色、prompt、介面、互動都變多，更難維護和除錯

兩頁的結論各一句：多個 agent 提供更多分配工作、資訊與責任的方式；但只有在合作的好處大於協調成本時，合作才有幫助。

四種編排模式 Overview · Independent · Centralized · Decentralized · Hybrid 重點

模式怎麼運作取捨
獨立 Independent（p.18）agent 之間不交換中間訊息；最後一步由聚合者合併或挑選各自的輸出可以平行，但 agent 無法根據彼此的中間發現調整做法

動態多 agent 架構：DyLAN Dynamic Multi Agent Architecture · DyLAN, Liu et al., 2023

前面的拓撲是人手動決定的。DyLAN 讓系統依任務自己挑團隊、自己調整結構，分兩階段：

  • 團隊最佳化（p.25–26）：先在幾題上試跑候選 agent，算出每個 agent 的「agent 重要性分數」，再組出這個任務專用的團隊。做法有三步：
    • 傳遞（Propagation）：agent 以前饋方式逐輪作答，每個 agent 替前一輪 agent 的回答打效用分。
    • 聚合（Aggregation）：答完後把功勞往回傳，依照誰對最終共識答案有貢獻來累加分數。
    • 選擇（Selection）：取分數最高的 agent。圖中例子四個 agent 的分數是 I₁=0.65、I₂=0.35、I₃=1.15、I₄=0.20，選出前兩名 agent 1 和 3。
  • 解題（p.27）：在新任務上執行時，用 LLM 為每個回答打效用分，動態把表現差的 agent 移出團隊（圖上稱 Agent Team Reformation）；當 2/3 的 agent 答案一致時就提早停止。
  • 結果（p.28，決策任務）：在更少的 API 呼叫下得到更高的成功率。

以對話作為溝通：AutoGen Multi-Agent Communication as Conversations · AutoGen, Wu et al., 2024

交接 vs 把 agent 當工具 Handoff vs Agent-as-tool · OpenAI Agents SDK 重點

  • 交接（Handoff，p.37）：控制權轉移，接手的 agent 變成主動方、繼續和使用者互動；相關的對話歷史與任務細節跟著轉過去。適合「應該由專家直接面對使用者、負責後續步驟」的情境。
  • agent 當工具（Agent-as-Tool，p.38）：呼叫方保有控制權，只送給專家一個範圍明確的請求與挑選過的上下文；專家回傳答案或產出物，呼叫方繼續工作。適合「由一個 agent 整合多位專家的貢獻、給出最終回覆」的情境。

  • 每個 agent 有角色設定檔，例如：名字 Alex、角色 Engineer、目標「寫出優雅、可讀、可擴充、有效率的程式」、限制「符合 PEP8 等規範、模組化、易讀易維護」。Engineer 從記憶取回 PRD 與系統設計，反覆寫程式、執行、除錯。
  • p.42：用軟體公司的標準作業程序（SOP）串起各角色：產品經理寫需求文件 → 架構師做系統設計 → 專案經理拆任務 → 工程師寫程式 → QA 工程師測試 → 驗收。例子是一句需求「寫一個經典又簡單的 Flappy Bird 遊戲」，最後老闆驗收：「不錯！我可以直接用鍵盤玩 Flappy Bird。」

訊息板的好處是 agent 不必知道彼此是誰，只要知道自己要訂閱哪類訊息；結構化文件（PRD、設計稿）也比自由對話更不容易在交接時遺漏資訊。

任務帳本：Magentic-One 與 Symphony Task Ledger · Magentic-One, Fourney et al., 2024 · Symphony 重點

  • p.54 任務帳本的四個作用：追蹤任務（記下目標、目前計畫與未解的問題）；追蹤執行（記下指派、相依關係、進度與阻礙）；引導決策（依目前狀態決定下一步跑什麼）；支援復原（執行卡住時更新計畫或重試）。一句話：任務帳本是一份明確、持續更新的工作紀錄，用來引導 agent 之間的協調。
  • p.55 Magentic-One：編排者 agent 維護兩層帳本。
    • 外層任務帳本（Task Ledger）：已知或已驗證的事實、要查的事實、要推導的事實、有根據的猜測、任務計畫。
    • 內層進度帳本（Progress Ledger）：每一步檢查任務完成了沒、是否陷入無效迴圈、有沒有進展、下一個發言者是誰、給它什麼指令。

    • 四個 worker：Coder（寫程式、推理）、ComputerTerminal（執行 Coder 寫的程式）、WebSurfer（瀏覽網頁、填表單）、FileSurfer（讀 PDF、pptx、WAV 等檔案）。

Worktree 隔離 Worktree Isolation

  • 問題：多個 agent 同時編輯同一個工作目錄，會互相覆寫。
  • 分開的工作空間：給每個 agent 自己的 checkout 與分支（圖：一個 git repo 底下有多個 worktree 資料夾，各自對應 main、bugfix、feature 分支）。
  • 受控的整合：把完成的貢獻 merge 回來、解決衝突、測試合併後的結果。
  • 取捨：隔離減少執行時的干擾，但各分支可能越走越遠，最後的整合工作變多。

補充：git worktree add ../agent-a -b agent-a 會在另一個資料夾建立同一個 repo 的新工作目錄，共用 .git 歷史但檔案互不影響。Claude Code 等 coding agent 平行跑多個 session 時常用這招。

自發的協調模式：CooperBench Emergent Coordination Patterns · Role Division · Resource Division · Negotiation · Khatua et al., 2026

CooperBench 讓兩個 coding agent 各自實作一個功能、但改到同一份程式碼，並觀察它們在對話中自己發展出哪些協調方式。三頁各一個實例：

角色分工agent 談好誰負責哪部分。Agent 1：「我加 section header 和 octal_str，你在兩者之間加 binary_str，維持字母順序。」Agent 2 先檢查 outlines/types/__init__.py 確認插入位置，回覆「在我的分支上依序插入 header → binary_str → octal_str」。
資源劃分agent 切分共享資源以避免碰撞。Agent 1：「我會改 llama_index/core/base/llms/types.py 第 68–84 行」。Agent 2：「我不會動 68–84 行，我會在第 84 行之後（從新的第 85 行起）插入 get_image_mimetype()」。
協商做法衝突時收斂到同一個計畫。Agent 1 檢查檔案後提出兩個選項：(1) 我加 IsHash，你加 import re 與 IsRegex，所有 __init__ 匯出由我處理；(2) 反過來。Agent 2：「選 (1)。我已經加了 import re，你加 IsHash，然後我加 IsRegex。」

這三種模式是 agent 自己想出來的，不是系統強制的。但 Part 5 會看到，即使會這樣協調，兩個 agent 合作的成功率仍明顯低於一個 agent 獨力完成。

#!/bin/bash
while true; do
    COMMIT=$(git rev-parse --short=6 HEAD)
    LOGFILE="agent_logs/agent_${COMMIT}.log"

    claude --dangerously-skip-permissions \
           -p "$(cat AGENT_PROMPT.md)" \
           --model claude-opus-X-Y &> "$LOGFILE"
done

--dangerously-skip-permissions 會跳過所有權限確認，只適合在隔離的容器裡用，這也是 p.88 每個 agent 都跑在獨立容器的原因。

學到的教訓 Lessons Learned 重點

  • 強的測試引導自主工作：可靠的正確性與回歸測試，讓 agent 知道自己有沒有進展、有沒有弄壞東西。
  • 為平行而設計：把失敗或子任務拆成可以分開處理的單位。
  • 讓協調明確化：認領任務、在各自的 clone 工作、透過 git 整合貢獻。
  • 跨 session 保存知識：維護共享文件、進度筆記，以及失敗嘗試的紀錄。
  • 讓回饋有效率：提供精簡的錯誤摘要、可搜尋的 log、快速的測試子集，以及定期的進度更新。
  • 指派互補的目標：給 agent 明確不同的職責。
