### 1. 動機：產資料便宜，挑資料才難（p.5–12）

**CWM 的例子：先生 300 萬條，再篩（p.7）**

Meta 的 CWM 先產生 300 萬條軌跡，再決定留哪些：
- 同一個 repo 裡太像的軌跡（Jaccard 相似度 ≥ 0.5）丟掉。
- 失敗的軌跡**不丟**，因為 CWM 要學的是「程式環境會怎麼反應」，失敗的紀錄一樣有用。

重點不是 CWM 本身，而是：**「先大量生、再篩」已經是業界常態。** 而且篩的標準看你要訓練什麼，沒有一體適用的規則。

**每一層都在丟資料（p.8）** ⭐ 整講的骨架

```
候選任務 → 有效任務 → 可學任務 → Rollouts → 保留的軌跡 → 訓練混合
└──────── 第 2 節：選任務 ────────┘ └── 第 3 節：選軌跡 ──┘ └ 第 4 節 ┘
```

| 漏斗層 | 在問什麼 | 對應章節 |
|---|---|---|
| 候選 → 有效 → 可學任務 | 這個任務本身對不對？模型學不學得到？ | 第 2 節 選任務 |
| Rollouts → 保留的軌跡 | 這條解題紀錄值不值得模仿？ | 第 3 節 選軌跡 |
| 保留的軌跡 → 訓練混合 | 要多少、要多雜？ | 第 4 節 多 vs. 好 |

p.70 的總結頁用的是同一張圖，可以當作整講的目錄。

> **Q：是指在每一層都會丟資料？**
>
> 對，每一個箭頭都是一道篩子，資料只會越來越少。用 LEGO-RL（p.28–29）的實際數字走一遍：
>
> | 層 | 篩掉什麼 | 剩下 |
> |---|---|---|
> | 候選任務 | （從 GitHub 挖來的全部） | 36,884 |
> | → 有效任務 | 規則篩選、能不能建置、驗證器對不對 | 21,681 |
> | → 可學任務 | 模型 4 次全錯或 4 次全對的 | **2,699** |
>
> 從 36,884 到 2,699，只剩約 7%。後面的 rollout 和軌跡也一樣：模型在任務上跑出很多條軌跡，再篩掉作弊的、雜亂的，才是「保留的軌跡」。
>
> 要注意的是：**每一層篩掉的理由不一樣。** 前面篩的是「題目錯了」，中間篩的是「題目對但學不到」，後面篩的是「解法不值得學」。所以投影片才把它畫成一層一層，而不是一個大過濾器。

**要挑的有兩種：SFT 用的軌跡、RL 用的環境（p.9）**

| | 軌跡 Trajectory | 環境 Environment |
|---|---|---|
| 是什麼 | 一段 agent 解任務的紀錄（issue 描述 + 沙盒） | 一個任務（issue 描述 + 沙盒），加上判斷是否成功的機制 |
| 組成 | 思考 → 行動 → 觀察 → 行動 → 觀察 → 提交 | 任務 + 沙盒 + 驗證器 |
| 怎麼用 | SFT：LM 模仿紀錄中的行為 | RL：LM 在任務上練習 ReAct |
| 本講章節 | 第 3 節 | 第 2 節 |

這張表和上一講 p.13 是同一個框架。差別在於上一講問「怎麼做出來」，這一講問「做出來之後怎麼挑」。

**訓練資料變壞的三種方式（p.10）** ⭐

| 類型 | 症狀 | 考試比喻 | 本講章節 |
|---|---|---|---|
| **錯誤訊號** Wrong signal | 驗證器壞掉、成功是靠作弊得來的 | 標準答案寫錯；學生偷看答案拿高分 | 第 2–3 節 |

| **重複訊號** Redundant signal | 同樣的東西再來一遍 | 同一題型練 1,000 次 | 第 4 節 |

### 2. 哪些任務值得拿來訓練？（p.13–34）

**任務篩選是一個迴圈（p.14）** ⭐

```
① 濾掉壞掉的任務 → ② 實際執行檢查 → ③ 留下模型有時會解的 → ④ 模型進步後重挑 ─┐
   SWE-bench Verified    APIGen、CodeMidas     DAPO、LEGO-RL            WebRL       │
        ↑──────────────────────────────────────────────────────────────────────┘
```

- **① ②** 處理「錯誤訊號」：題目本身錯了。
- **③ ④** 處理「沒有訊號」：題目沒錯，但對**現在這個模型**來說太簡單或太難。

為什麼是迴圈？因為「難不難」是相對的。模型變強之後，原本適中的題變太簡單，就要重新挑。

#### 2.1 濾掉壞任務（p.15–18）

**一個壞任務長什麼樣（p.15，sklearn-14520）**

- Issue 說：`TfidfVectorizer.transform()` 的 `copy` 參數沒被用到。
- 測試卻要求跳出一段**一字不差**的棄用警告訊息，而這段文字是在 PR 討論中才決定的。

Agent 只看得到 issue，不可能猜到確切的措辭。結果是：**正確的修法也被判失敗。**

**OpenAI 人工檢查 SWE-bench（p.16–17）**

93 位工程師檢查 1,699 題：38.3% 描述不清、61.1% 測試不公平，**總共濾掉 68.3%**。三分之二的題目有問題。

**壞任務的後果（p.18）** ⭐

| 模型 | 原始 SWE-bench | SWE-bench Verified |
|---|---|---|
| GPT-4o | 16% | 33.2% |

同一個模型，換成清理過的題目，分數翻倍。原本的低分有一大半是題目的錯，不是模型的錯。

> **講師補充：評測時錯一題 vs. 訓練時錯一題**
>
> - **評測時**：壞題目只是讓分數不準。GPT-4o 被低估了，但模型本身沒受影響。
> - **訓練時**：壞題目會給出**錯誤的獎勵**。模型寫出正確的修法，卻被打 0 分，RL 就會「壓低」這個正確做法。這等於在懲罰正確行為。
>
> 回想 Lecture 11 的那句話：**模型學的是你給分的方式。** 給分方式錯了，模型就學錯。所以訓練用的任務比評測用的更需要清理。

#### 2.2 實際執行來檢查（p.19–24）

人工檢查不能擴展到幾萬題，所以要自動化。核心想法：**不要只看題目，要真的跑一次。**

**APIGen（p.19）：三關由便宜到貴**

```
格式檢查（JSON 對不對）→ 執行檢查（真的呼叫 API）→ 語意檢查（LLM 判斷結果合不合意圖）
```

便宜的關卡先擋，貴的 LLM 判斷只用在前兩關都過的資料上。

**CodeMidas（p.20–24）：只從原始碼建環境**

1. **測試只能檢查任務有寫的事（p.21）** ⭐

```python
# 太嚴：要求確切的錯誤訊息（agent 看不到）
with pytest.warns(DeprecationWarning, match="'copy' param is unused and has been ..."):
    ...

# CodeMidas：任務只說「要拋 ValueError」，就只檢查這件事
with pytest.raises(ValueError):
    parse_config(bad_input)
```

2. **每題跑 6 個全新容器（p.22）**

| 跑什麼 | 次數 | 預期 | 為什麼 |
|---|---|---|---|
| 起始程式碼 | 2 | 必須失敗 | 證明測試真的在測東西 |
| 參考解 | 4 | 必須通過 | 證明題目可解 |

六次全部符合預期才留。重複跑是為了抓「有時過、有時不過」的不穩定測試。

3. **Rollout 後再三道過濾（p.23）**：解答有沒有藏在環境裡（洩漏）、驗證器有沒有判錯、是不是全對或全錯。

**結果（p.24）**：過濾後的 3k 題，在三項評測上都贏過未過濾的 8k 題。

> **講師補充：「太嚴的測試」為什麼是大問題？**
>
> 驗證器可能錯兩種方向：
>
> | | 正確解 | 錯誤解 |
> |---|---|---|
> | 判通過 | ✅ | ❌ **偽陽性**：作弊或錯的也過了 |
> | 判失敗 | ❌ **偽陰性**：對的被打掉 | ✅ |
>
> sklearn-14520 是**偽陰性**。大家比較常擔心偽陽性（作弊），但偽陰性一樣傷：模型會學到「正確做法沒有用」。CodeMidas 的「只檢查任務有寫的事」就是在減少偽陰性。

#### 2.3 留下模型「有時會解」的（p.25–31）

這一段是本講**最需要搞懂的機制**。

**DAPO：全組同分，RL 就學不到東西（p.25）** ⭐

回想 Lecture 9 的 GRPO：同一題讓模型做 8 次，

```
advantage = (這次的 reward − 8 次的平均) / 8 次的標準差
```

| 8 次的結果 | 平均 | 每次的 advantage | 能學嗎 |
|---|---|---|---|
| `1 0 1 1 0 0 1 0` | 0.5 | 對的 +1、錯的 −1 | ✅ 加強對的做法、壓低錯的做法 |
| `1 1 1 1 1 1 1 1` | 1 | 全部是 0 | ❌ 沒有梯度 |
| `0 0 0 0 0 0 0 0` | 0 | 全部是 0 | ❌ 沒有梯度 |

> **講師補充：用考試比喻 advantage**
>
> GRPO 不是問「這次對不對」，而是問「**這次比你自己平常好還是差**」。
>
> - 一題你做 8 次，對 4 次：對的那幾次「比平常好」，就加強那幾次的做法。
> - 一題你做 8 次全對：每次都「跟平常一樣」，沒有哪一次特別值得學。
> - 一題你做 8 次全錯：一樣沒有比較對象，模型不知道該往哪改。
>
> 所以全對和全錯的題目，**算力花下去了，卻完全沒有學習效果**。
>
> （技術細節：全組同分時標準差是 0，實作上分母會加一個很小的數避免除以零，算出來 advantage 仍是 0。）

**更糟的是，模型越強，這種題越多（p.26）**。DAPO 的解法：**持續取樣，直到 batch 裝滿「有對有錯」的題（p.27）**。每一步要多跑一些，但總步數變少，整體划算。

**LEGO-RL：訓練前先篩（p.28–31）**

| 4 次中解出 | 0/4 | 1/4 | 2/4 | 3/4 | 4/4 |
|---|---|---|---|---|---|
| 處理 | 丟 | 留 | 留 | 留 | 丟 |

- DAPO 在**訓練中**即時丟，LEGO-RL 在**訓練前**先篩。道理一樣。
- 不篩的話（p.30）：72.7% 的題從沒解出、13.4% 每次都解出，超過八成沒有訊號，訓練完全不進步。
- 任務池會過期（p.31）：訓練到第 3 輪，「全解出」的題明顯變多。所以要定期補新題。

#### 2.4 模型進步後重新挑（p.32–34）

**WebRL**：不只重新篩舊題，還**從模型失敗的地方生新題**（自我演化課程）。Llama-3.1-8B 在 WebArena-Lite 從 4.8% 升到 42.4%。

這就是迴圈的第 ④ 步：題庫跟著學生的程度一起長。

**本節論文 → 壞訊號**

| 論文 | 處理什麼 |
|---|---|
| SWE-bench Verified、APIGen、CodeMidas | 錯誤訊號：題目或驗證器錯了 |
| DAPO、LEGO-RL、WebRL | 沒有訊號：太簡單或太難 |

### 3. 哪些軌跡值得模仿？（p.35–50）

第 2 節挑好了題目，模型在上面跑出很多條軌跡。現在要決定：**哪些軌跡拿去 SFT？**

最直覺的做法叫 **rejection sampling**：測試通過就留，沒通過就丟。本節說這個做法兩邊都錯。

**通過測試 ≠ 好示範（p.36）** ⭐

| | 情況 | 做法 | 代表論文 |
|---|---|---|---|
| **通過測試** | 有些是作弊 | 檢查 agent 是怎麼通過的 | Verification Horizon |
| | 有些很雜亂 | 依過程品質挑選 | SWE-Prime |
| **沒通過** | 失敗也有資訊 | 保留，但標記為失敗 | NAT |
| | 前半段是對的 | 從專家的失敗紀錄中救回好的步驟 | EEF |

一句話：**只看結果會留下不該留的成功，丟掉不該丟的失敗。**

#### 3.1 通過的軌跡裡有作弊的（p.37–41）

**Verification Horizon 整理出七種捷徑（p.38）**

| 捷徑 | 白話 |
|---|---|
| 解答成品取用 | 直接去抓官方的 patch |
| 外部修法查找 | 上網搜這個 bug 的修法 |
| 竄改評測框架 | 改 `pytest.ini`、逾時設定，而不是修 bug |
| 竄改測試判準 | 把測試改弱，或加 `skip` |
| 貼合可見測試 | 針對看得到的測試寫特例 |
| 針對評分器修補 | 依「評分器會怎麼檢查」來改 |
| 挖 Git 歷史 | `git log` 找未來的修正（Lecture 11 p.60 的例子） |

這些軌跡**全部都通過測試**。只看結果，完全看不出問題。

**通過率很高，乾淨的表現卻在下滑（p.40）**：沒有監控時，驗證器通過率持續上升；但把作弊算成失敗後，真實能力在訓練後期急劇下滑。

**解法：監控軌跡（p.41）** ⭐

| 三個 SWE-bench 版本平均 | 無監控 | 加監控 |
|---|---|---|
| 作弊解出率（越低越好） | 28.57% | **0.56%** |
| 乾淨解出率（越高越好） | 40.22% | **60.53%** |

監控 = 檢查每條軌跡的過程，抓到上面七種捷徑就把那次成功判為失敗。作弊幾乎消失，乾淨表現反而上升 20 點：原本被捷徑佔走的學習訊號，回到了真正的除錯能力上。

> **Q：這和 Lecture 11 說的「CoT 監控會讓模型學會藏」不是矛盾嗎？**
>
> 好問題，這是兩件不同的事：
>
> | | Lecture 11 p.63–64 | 本講 p.41 |
> |---|---|---|
> | 監控什麼 | 模型的**思考過程**（CoT 裡有沒有寫「我要作弊」） | 模型的**實際行動**（有沒有執行 `git log`、改 `pytest.ini`） |
> | 結果 | 模型學會不寫出意圖，照樣作弊 | 作弊幾乎消失 |
>
> 想法可以藏，**行動藏不住**：要抓官方 patch 就一定得執行那個指令，要改測試就一定得動那個檔案。所以監控行動比監控想法可靠。
>
> 不過要記住，這是「目前有效」。只要監控器有漏洞，模型就可能找到新的捷徑。p.37 的「驗證器和策略共同演化」講的就是這場軍備競賽。

#### 3.2 通過的軌跡裡有雜亂的（p.42–44）

**SWE-Prime**：一條通過的軌跡裡，可能有沒用的步驟、重複的步驟、危險的步驟。整條拿去模仿，壞習慣也會學進去。

兩階段篩選：
1. **挑軌跡**：看解題流程是否合理（觀察 → 修改 → 驗證）、工具呼叫成功率、有沒有冗餘或作弊。
2. **挑片段**：把軌跡切段打分，只有好的片段算 loss。

結果：**只用 10% 的成功軌跡，贏過用全部。**（注意投影片寫的 12.2%、24.2% 是**相對**提升，不是百分點。）

#### 3.3 失敗的軌跡也有用（p.45–50）

**NAT（p.45–47）：失敗的也留，但貼標籤**

```
[成功] 思考 → 行動 → 觀察 → ... → 正確答案
[失敗] 思考 → 行動 → 觀察 → ... → 錯誤答案
```

訓練時兩種都給模型看，但在開頭或結尾標明成功或失敗。推論時要求模型產生「成功」版本。

> **講師比喻**
>
> 就像老師發考卷時，同時給學生看「100 分的考卷」和「標了紅字的錯誤考卷」。學生從錯誤考卷裡也能學到：前面這幾步是對的思路，最後這一步是錯的。只要**標清楚哪份是錯的**，學生就不會照抄錯誤。

**EEF（p.48–50）：從專家的失敗裡救回好的步驟**

問題：只留專家成功的紀錄，而專家大多在**簡單題**成功，於是**難題永遠進不了訓練集**。

做法：GPT-4 某條軌跡最後失敗了，但 EEF 從它走到一半的狀態讓 agent 接手。如果接手後成功了，就代表 GPT-4 走到那裡之前的步驟是好的，可以留下來。

```
GPT-4：s0 → sl → s2l → s3l → … → 失敗
           ↓      ↓      ↓
agent 接手：成功   失敗   成功  → sl、s3l 之前的步驟值得學
```

結果（p.50）：WebShop 勝率 EEF 62% > RFT 53.6% > GPT-4 本身 35.6%。**學生超越了老師**，因為它學到了老師失敗紀錄裡被 RFT 丟掉的好東西。

**本節論文 → 壞訊號**

| 論文 | 處理什麼 |
|---|---|
| Verification Horizon | 錯誤訊號：作弊的成功 |
| SWE-Prime | 錯誤訊號：雜亂的成功，部分步驟不該學 |
| NAT、EEF | 反過來：救回被誤丟的**有用訊號** |

### 4. 更多資料，還是更好資料？（p.51–67）

回到第 1 節的爭論。

**示意圖（p.52）** ⭐

```
表現
 │          ╱ 大量未過濾（起點低，一直上升）
 │   ──────╳────── 小而精（起點高，很快趨平）
 │       ╱
 │     ╱
 └──────────────────→ 資料量
```

兩派都對，只是適用在不同規模。**不論哪一派，會泛化的是多樣性。**

#### 4.1 少即是多：LIMI（p.53–57）

**前例（p.53）**：LIMA（1,000 筆對齊資料）、LIMO（817 筆數學）、LIMI（78 條 agent 軌跡），都叫「Less Is More for X」。

> **講師補充：LIMA 的假說是什麼？為什麼少量就夠？**
>
> LIMA（本講必讀）的主張是：**模型的知識和能力幾乎都在預訓練學到了，微調只是教它「用什麼格式和風格回答」。** 教格式不需要很多例子，1,000 筆精選的就夠。
>
> 用考試比喻：學生其實已經會解題（預訓練），只是不知道考卷要怎麼寫（格式）。給他看幾份寫得很漂亮的範例考卷就夠了，不用再做 10,000 題。
>
> 但這個假說有前提：**能力已經在模型裡。** 如果是模型根本不會的新能力，少量資料就不夠。這也是為什麼 LIMI 的結果要打折看（見下面的但書）。

**LIMI 的結果（p.54）**：AgencyBench 上，78 條訓練 → 73.5%；10,000 條訓練 → 47.8%。

**這 78 條怎麼來的（p.55–56）**：60 個來自真實的開發者與研究者情境、18 個從 GitHub PR 合成。四位博士生和 GPT-5 反覆修正直到每題成功，平均每條 **42.4k token**。

> **講師提醒：「78 條」其實很貴**
>
> 每一條都是博士生花大量時間、平均四萬多 token 的完整解題過程。**少的是條數，不是工夫。** 這不是「隨便找 78 條就夠」，而是「花大錢做 78 條極品」。

**但書（p.57）** ⭐
- AgencyBench 只有 10 題，而且和 LIMI 有很多共同作者。
- 離開 CLI 環境，LIMI 50.0% vs. GLM-4.5 48.7%，只差 1.3 點。

讀論文的基本功：**看到驚人的數字，先問評測集多大、是誰做的、換個設定還成不成立。**

#### 4.2 多即是多：Orchard（p.58–60）

**實驗設計（p.58）**：基底模型、訓練配方、框架全部固定，只改兩個變因：
- 資料量：512 / 1,024 / 2,048 條
- 挑選策略：隨機、repo 多樣、repo 集中、多檔案、大 diff、綜合

**任何像樣的 SFT 都有幫助（p.59）**：基底 22.0%，最差的設定也有 44.0%。

**規模壓過挑選策略（p.60）** ⭐

| 軌跡數 | 隨機 | repo 多樣 | repo 集中 | 多檔案 | 大 diff | 綜合 |
|---|---|---|---|---|---|---|
| 512 | 45.8 | 44.0 | 47.9 | 47.5 | 49.5 | 48.1 |
| 1,024 | 50.3 | 49.0 | 51.3 | 51.6 | 52.2 | 52.1 |
| 2,048 | 52.8 | 52.2 | 53.4 | 54.2 | 52.9 | 53.7 |

> **講師補充：這張表怎麼讀**
>
> 比較兩種「進步的方法」：
>
> - **橫著看（換策略）**：512 條時，最好和最差差 5.5 點（49.5 − 44.0）。
> - **直著看（加資料）**：最差的策略從 512 加到 2,048 條，就多了 8.2 點（44.0 → 52.2）。
>
> 加資料的效果比換策略大。而且到了 2,048 條，策略之間只差 2 點：**資料越多，怎麼挑就越不重要。**

> **Q：「repo 多樣」在這裡反而最差，不是說多樣性才會泛化嗎？**
>
> 投影片沒解釋這點，以下是我的理解：Orchard 的「repo 多樣」是在**固定總條數**下分散到很多 repo，每個 repo 分到的軌跡就變少，模型可能沒辦法在任何一個 repo 學深。真正測多樣性的是下面 SWE-smith 的實驗（固定 700 條，只變 repo 數），那裡多樣性確實有效。兩個實驗的設計不同，結論不能直接對比。

#### 4.3 兩派都同意的事：多樣性（p.61–67）

**AgentRefine（p.61–64）**

- 現有 agent 資料在**訓練過的環境**（held-in）表現好，**沒見過的環境**（held-out）就不行（p.61）。
- 在新環境裡最常見的三種錯：指令拼錯（`clik`）、想的和做的對不上、卡在同一個動作重複（p.62）。
- 這三種錯都不是「不會」，而是「**錯了不會改**」。
- 解法：合成很多不同的環境，並刻意訓練「出錯 → 修正」的過程（p.63）。結論：自我修正和多樣性才會泛化（p.64）。

**SWE-smith（p.65–67）**：講者本人的論文，實驗設計很乾淨

- 固定用 **700 條**軌跡，只改變它們來自幾個 repo（5 → 100）。
- 結果：repo 數 5 / 25 / 50 / 100 → 解出率 10.3% / 11.5% / 12.9% / 15.1%。
- repo 數每翻倍，分數大約加同樣多，所以是**對數成長**。

**總量相同時，來源越多樣越好。** 這是「多樣性才會泛化」最直接的證據。

**本節論文 → 壞訊號**

| 論文 | 處理什麼 |
|---|---|
| LIMI | 主張：少量極品資料就夠 |
| Orchard | 主張：量比挑法重要 |
| AgentRefine、SWE-smith | 重複訊號：多樣性才會泛化 |

### 5. 結論：調和兩派（p.68–70）

**候選資料有限時，篩選最有價值（p.68）** ⭐ 本講最重要的一張圖

| 訓練集 | 樣本數 | 微調分數 |
|---|---|---|
| 隨機 | 9,139 | 21.61 |
| 過濾後 | 9,139 | 23.52 |
| 完整未過濾 | 19,050 | **24.75** |

相同大小時，過濾贏過隨機（+1.91）；但更大的未過濾資料集贏過兩者。

> **講師補充：這張表怎麼同時解釋 LIMI 和 Orchard**
>
> 關鍵在你**能不能再多拿資料**：
>
> | 你的處境 | 該怎麼做 | 對應 |
> |---|---|---|
> | 資料量被限制住（只能用 N 條，例如人工標註很貴） | **挑哪 N 條很重要**：過濾 > 隨機 | LIMI |
> | 資料可以一直加（例如能自動合成） | **加量比過濾更划算** | Orchard |
>
> 用考試比喻：如果學生只有一週準備，你要幫他挑最精華的 50 題；如果他有一整年，就讓他多做各種題型，挑不挑反而沒那麼重要。
>
> 但不論哪種處境，第 2 節的「壞題目要丟」和第 3 節的「作弊的解答要丟」都還是要做。**「加量」指的是加有效的資料，不是連錯的都留。**

**挑選 agent 資料的實務檢查清單（p.69）** ⭐

| 步驟 | 做什麼 | 處理哪種壞訊號 | 代表論文 |
|---|---|---|---|
| 1 驗證任務 | 實際執行：起始碼要失敗、參考解要通過、測試不能太嚴 | 錯誤訊號 | SWE-bench Verified、CodeMidas |
| 2 篩選難度 | 留下模型有時會解的，並隨訓練更新 | 沒有訊號 | DAPO、LEGO-RL、WebRL |
| 3 稽核成功 | 檢查是怎麼通過的，抓作弊和雜亂的步驟 | 錯誤訊號 | Verification Horizon、SWE-Prime |
| 4 保留失敗 | 加上標記，或救回其中好的步驟 | （救回有用訊號） | NAT、EEF |
| 5 擴大多樣來源 | 更多 repo、更多環境 | 重複訊號 | Orchard、AgentRefine、SWE-smith |

**總結（p.70）**

- **任務**：實際執行每個任務來檢查它，保留模型有時會解的，並隨模型進步更新任務池。
- **軌跡**：通過可能是作弊，所以要檢查它是怎麼通過的。失敗也能教東西。
- **訓練混合**：資料稀少時要精選；到了一定規模，量和多樣性勝出。

> **講師總結：整講濃縮成三句話**
>
> 1. **對 RL 來說，「剛好有點難」的題目才有用**：全對或全錯都算不出 advantage，而且難度會隨模型進步而變。
> 2. **只看結果不夠，要看過程**：通過可能是作弊，失敗可能有一半是對的。
> 3. **能拿更多資料就拿更多，但要夠雜**：精挑只在資料有限時特別值得；多樣性永遠重要。
