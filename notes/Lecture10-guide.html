PART 1 · p.2–12

軟體工程的興起：演繹式的技術開發

用「把一個數加 5」這件事，看程式設計怎麼從機器碼一路抽象到高階語言，並引出「人寫規則、程式執行規則」的演繹式開發。

2–9

同一件事的三種寫法 The rise of software engineering

投影片一頁寫年代、下一頁寫那個年代的程式長什麼樣子，三組做的都是同一件事：把暫存器（變數）的值加 5。

1940s 數值指令
48 83 C0 05（p.3–4）→1950s 初 組合語言

  • p.3–4：最早直接寫給 CPU 的數字指令。48 83 C0 05 正是 x86-64 的 add rax, 5 機器碼（48 表示 64 位元運算、83 C0 是「對 rax 加上一個小常數」、05 是常數 5），本導讀已核對。
  • p.5–6：組合語言用人看得懂的助記符取代數字，但還是一條對一條地對應機器指令。
  • p.7：John Backus（FORTRAN 的發明者）的話：1950 年代很多程式設計師把自己當成「祭司」，守護著一般人無法理解的技藝與奧秘。意思是當時寫程式是少數人的專門技能。
  • p.8–9：高階語言讓人只描述「要做什麼」，翻譯成機器碼交給編譯器。每一步都是把人從細節裡解放出來。

這條歷史線是為 p.17 埋伏筆：抽象層一路往上疊，下一層就是 ML、LLM 與 agent。

10–12

演繹式的技術開發 Deductive technology creation 重點

  • p.10：Tony Hoare 1969 年的論文《An Axiomatic Basis for Computer Programming》：程式設計是一門精確的科學，程式的所有性質和執行後果，原則上都能只靠閱讀程式本身、用純演繹推理推導出來。
  • p.11 把這種開發方式總結成一個公式：規則 + 輸入 → 輸出。人寫規則（程式碼），程式把規則套用在新的輸入上。
  • p.12：IBM 1954 年的 FORTRAN 初步報告宣稱「FORTRAN 應該能幾乎消滅編碼和除錯」。這句話放在這裡有點反諷：每一代新抽象都這樣承諾過，但寫程式和除錯從來沒有消失。

記住 p.11 的公式，p.15 會把它整個反過來。

PART 2 · p.13–22

ML 的興起：歸納式的技術開發

機器學習把公式反過來：人給輸入和輸出，由訓練推出規則。講者主張所有數位技術開發都正在變成歸納式。

13–14

ML 的興起 The rise of ML 圖片頁

  • p.14 是一篇文章截圖：Chris Anderson 2008 年 6 月 23 日的〈The End of Theory: The Data Deluge Makes the Scientific Method Obsolete〉（理論的終結：資料洪流讓科學方法過時）。
  • 文章開頭引用統計學家 George Box 的名言「所有模型都是錯的，但有些有用」，接著主張：過去只有模型能解釋世界，如今有了海量資料，公司可以不必先建立理論。

講者用這篇文章代表「讓資料說話」的思潮，也就是歸納式開發的起點。

15–16

歸納式的技術開發 Inductive technology creation 重點

  • p.15 的公式和 p.11 相反：輸入 + 輸出 → 規則。人提供範例（資料與標籤），由訓練推論出規則，也就是模型。
  • p.16 用兩條流水線對照兩種開發生命週期：
生命週期性質步驟
軟體工程（SWE）演繹式規格 → 實作 → 測試 → 部署（一條直線）
機器學習（ML）歸納式目標 → 評測 → 實驗 → 優化，再從優化回到評測反覆迭代

關鍵差異：軟體工程的「測試」在實作之後，是驗收；ML 的「評測」在實驗之前，是整個迭代迴圈的中心。

所有數位技術開發都在變成歸納式 All digital technology development is becoming inductive 重點

  • p.17：演進路線是 軟體 → ML → LLM → Agent。
  • p.18：Claude Shannon 的話：「我最大的夢想，是有一天造出一台真正會思考、學習、和人類溝通，並能以相當複雜的方式操作環境的機器。」最後一項「操作環境」正是 agent。
  • p.19–20：講者的核心主張是所有數位技術開發都在變成歸納式，分三層：
    1. 模型：從資料學出來。
    2. Agent：靠評測開發出來。
    3. 軟體：由 agent 產生。

第三點是推論：如果軟體由 agent 寫，而 agent 又是靠評測調出來的，那麼最終決定軟體品質的就是評測。這是整講的動機。

從規格到評測

用一個抽取電話號碼的小程式說明：當實作換成 LLM，「真相的來源」就從規則變成輸出。

23–25

規則與輸出，誰是真相的來源？ Rules vs. outputs as the source of truth 重點 圖片頁

p.24 是傳統寫法，用正規表示式抽電話號碼：

def extract_phone_number(text):
    match = re.search(r"\d{3}-\d{3}-\d{4}", text)
    return match.group()

p.25 用 diff 的樣子把那兩行（紅色）換成呼叫 LLM（綠色）：

    response = OpenAI().responses.create(
        model="gpt-5.5",
        input=f"Extract the phone number:\n\n{text}",
    )
    return response.output_text
  • 正規表示式版本：規則寫在程式碼裡，讀程式就知道它會做什麼（呼應 p.10 Hoare 的說法）。遇到 (555) 123 4567 這種格式就抓不到，但這點也能從規則推出來。
  • LLM 版本：程式碼裡已經沒有規則了，只有一句自然語言。它對各種輸入會輸出什麼，只能靠跑大量例子看輸出來判斷。所以真相的來源從「規則」移到了「輸出」。
source of truth真相的來源regular expression正規表示式

Harbor 的任務格式 TASK 重點

my-task/
├── instruction.md      # 給 agent 的指令
├── task.toml           # 設定（時間限制、資源等）
├── environment/
│   └── Dockerfile      # agent 工作的環境
├── solution/
│   └── solve.sh        # 參考解答
└── tests/
    └── test.sh         # 驗證器

（註解為本導讀補充；task.toml 的具體欄位投影片沒有列出。）這種格式要達到五個性質：

  • 與 agent 無關：任何 agent 都能拿來跑，不綁定某個產品。
  • 容易定義：一個資料夾、幾個檔案就是一個任務。
  • 可攜：靠 Docker，在本機或雲端都能跑。
  • 表達力強：只要能在容器裡做的事都能當任務。
  • 彼此獨立：每個任務自成一體，不依賴其他任務。

對照 p.38：instruction.md、environment/、tests/ 正好是那三個部分，再加上 solution/（p.53）和設定檔。

PART 6 · p.44–55

怎麼寫好一個任務

依任務資料夾的組成逐項講：指令、環境、驗證器、防止 reward hacking、參考解答，每項附上審查前後的對照。

44

寫任務的三個原則 Writing Tasks 重點

副標是兩個問題：你在量什麼？你量得對嗎？

  • 指令與驗證器要對齊：指令要求的事，驗證器都要檢查；驗證器檢查的事，指令都要講到。
  • 防止 reward hacking：不讓 agent 用作弊的方式拿到分數。
  • 真實、公平、有趣：任務要像真實工作、不能有藏起來的陷阱，也要值得測。

指令 Instructions

副標：依你的目標，可能要在不同情境下測量。Terminal-Bench 的指令原則有三：

  • 完整明確：驗證器會檢查的要求都要寫出來。
  • 盡量精簡：agent 自己從環境查得到的資訊就不要寫。
  • 盡量自然：像真人會下的指令，而不是模板。

p.46 是一個實際的審查前後對照（圖片頁）：任務是寫 FreeCAD 腳本修改一個半開式葉輪（impeller）的參數。

原版一大頁：逐條列出零件結構、每個尺寸參數、限制條件、FreeCAD 版本號，還有粗體小標題與排版。
審查意見（RyanMarten 的留言）在保持完整明確的前提下把指令縮到最短；agent 能從環境查到的資訊（例如 FreeCAD 版本）不要寫；拿掉多餘的 LLM 式排版（粗體、破折號）和模板，只講要求、哪些部分會被評分、要產出哪兩個檔案。
改版幾段話：要產出哪兩個 FCStd 檔、葉片數從 12 改為 6、其餘尺寸不變、葉輪的幾何描述與參數。

留言最後一句說這就是「Terminal-Bench 風格的指令」。指令寫得越囉唆，越像在幫 agent 解題，測到的能力就越少。

環境 Environments

副標：環境是 agent 行動的地方，要盡可能貼近「正式環境」的分佈。

  • 附加輸入：把文件、程式碼、狀態等材料放進環境。
  • 真的軟體／服務優於模擬（mock）：需要資料庫就真的起一個資料庫容器（多容器環境）。
  • 盡量開放：允許上網更真實，但也有代價（例如可能查到答案，見 p.52）。
  • 把網路依賴預先打包進環境以減少不穩定：例如套件先在 Dockerfile 裝好，免得某次評測因為下載失敗而算 agent 失敗。

p.48 是環境的審查前後對照（圖片頁）：目標是一張「Happy New Year 2025」海報，agent 要從候選素材裡挑圖組出來。原版的候選素材只有寥寥幾張；改版後素材大幅增加，混入了目標圖裡沒有的干擾項（例如另一種氣球、用電腦的人物、進度條）。從圖判讀，改動的用意是讓環境更像真實情況，agent 必須真的分辨哪些素材用得上，而不是全部拿來用。

驗證器 Verifiers 重點

副標：驗證器是以結果為準、對環境最終狀態做判斷的分類器。

  • 混淆矩陣：把驗證器當分類器看，它也會誤判。偽陽性（沒做對卻通過）會高估 agent；偽陰性（做對卻沒通過）會低估 agent。（投影片寫「FP/NP/TP/TN」，NP 應是 FN 的筆誤。）
  • 和指令裡的要求一對一對應：每條要求有一個檢查，每個檢查都對應一條要求。p.38 的九個 assert 就是例子。
  • 兩種做法：程式化檢查，以及 agent／LLM 當評審。

參考解答 Solution

  • 參考解答的用途是替驗證器和環境除錯：如果正確解答跑不過測試，問題在任務本身，不在 agent。
